# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`devflow` is a Claude Code plugin (and its own single-plugin marketplace, `.claude-plugin/marketplace.json`). It ships a working method: skills that orchestrate fresh subagents with pinned models, plus hooks and a CI tool that turn process rules into checks. The Python is standard library only; there is no build step and no dependencies. The one exception is the `review-ui` skill's web path, which ships Node scripts and needs Node 22+ and a Chrome-family browser.

## Commands

```
python -m unittest discover -s tests
python -m unittest tests.test_guard
python -m unittest tests.test_guard.<TestClass>.<test_name>
python hooks/session_start.py --next-step
python tools/eval_select.py select [--release] [--repo PATH]
python tools/eval_select.py record evals/results/<timestamp>/aggregate-result.json [--repo PATH]
python tools/eval_cost.py evals/results/<timestamp>/aggregate-result.json [--root DIR]
python tools/model_check.py --board [PROJECT] [--model "<line>"] [--part "<line>"] [--run SOURCE] [--config PATH]
python tools/model_check.py [SOURCE] [--model "<role>: <Model>, <effort>"] [--part "implementer: <Model>, <effort>"] [--escalated] [--diagnosis] [--config PATH] [--count N] [--exclude ID]
```

The hooks run in consumer projects as `uv run --no-project python …`. The CI check runs as `python tools/devflow_checks.py version|comments|attribution [--base SHA] [--head REF] [--repo PATH]`.

## Architecture

The plugin is mostly prompts and config; the only real code is the Python in `hooks/` and `tools/`.

- **Skills** (`skills/*/SKILL.md`): `setup`, `add-feature`, `fix-bug`, `release`, `manage-project`, `next-step`, `review-ui`. The orchestrating session runs these and delegates every phase to an agent (`next-step` and `review-ui` delegate to none; `next-step` runs `hooks/session_start.py --next-step` and hands the step to `add-feature` or `fix-bug`, which claim it). `fix-bug` and `release` reuse the `add-feature` pipeline, so changes to shared rules (stop rules, claiming a plan step, gates, the briefs' verbatim-paste requirement) usually need to be mirrored across the skills. `review-ui` is standalone: it does not delegate to agents, reads **Design system** and **See it working** when the profile exists and works without it, and `skills/review-ui/vendor/` is third-party code to be updated only by re-copying from upstream.
- **Agents** (`agents/*.md`): `locator` (Haiku), `designer` (Opus, medium effort; `fix-bug`'s diagnosis takes the board's `designer.diagnosis`, Opus, medium by default), `reviewer`, `planner` (Opus, medium effort), `implementer`, `tester` (Sonnet). Those pins in each agent's frontmatter are the defaults; a project sets its own in the `models` board in `.claude/devflow.json`, and every agent call passes what `tools/model_check.py --board` prints for its role (nothing where board and pin agree). A step's Model line or a design's part goes over the board; the locator, reviewer and planner never go below their pins, nor `fix-bug`'s diagnosis below Opus, medium. No default devflow picks (pin, phase default, floor, the effort the docs give a tab) is above Opus, medium; a board entry, Model line or part may go higher.
- **Project profile contract**: skills never hardcode project facts. They read `.claude/devflow.md` in the consumer project by exact heading (Project, Where things live, Architecture rules, Verify, Edit bounds, Escalate, See it working, Design system, Release, Try it, Standing rules) and paste sections verbatim into agent briefs. Renaming a heading in `templates/devflow.md` breaks every skill that cites it.
- **Config contract**: `.claude/devflow.json` in the consumer project configures the guard, the CI checks and the `models` board (schema example in `templates/devflow.json`). Without that file the hooks are no-ops: `hooks/hooks.json` gates each command on the file's existence.
- **`hooks/guard.py`** (PreToolUse on Bash, PowerShell, Write, Edit, MultiEdit, NotebookEdit, Read, Grep, Glob): parses shell commands across bash, PowerShell and cmd (splitting, quoting, heredocs, wrapper commands, `cd` tracking, env-var assignments) and returns allow, ask or deny. Exit 2 with a stderr reason is a deny; a JSON `permissionDecision: "ask"` on stdout is an ask. It denies writes to the project's real data (including globs and command substitutions that may reach it) and anything naming secrets, including the Read, Grep and Glob tools, refuses to start the app against real data unless the isolating env vars point at scratch, denies maintainer-only scripts, and denies git operations that would discard uncommitted status and plan edits (status file and plans folder). It asks before `gh release` writes and forced pushes, and where `guard.release_stamp` is set it denies publishing (`gh release create`, `upload`, a publishing `edit`, `gh api` writes) unless the gate's pass stamp names the current HEAD and the bound file's current hash. An unexpected exception, a missing `uv` or a guard that cannot start produces an ask ("not checked") rather than letting the call through silently; the `hooks.json` command wraps the guard to do this.
- **`hooks/session_start.py`**: prints branch, uncommitted files, CI state on HEAD and the plan's next open step, skipping steps another tab has claimed; when no open step of the current plan can start (claimed, at an uncleared Gate, waiting on a human or a skill, or needing a step that isn't done), it shows the next plan's first ready step instead, marked as from the next plan. `choose_step` makes that decision for both the summary and `--next-step`, which prints the plan, step and skill to run or the stop reason and what the maintainer does next. All subprocess calls share one deadline.
- **`tools/devflow_checks.py`**: CI check. `version` fails commits that change a configured version file unless the commit is titled `Release candidate X.Y.Z-rcN` or `Release X.Y.Z`, and fails a release-titled commit that leaves any listed version file at another version. `comments` fails new Python comment lines in configured folders, tokenizing old and new files so moved comments pass. `attribution`, where `.claude/devflow.json` sets `"attribution": "none"`, fails a commit whose message carries a `Co-Authored-By:` line naming Claude or a "Generated with Claude Code" line.
- **`tools/eval_select.py`**: lists the eval cases a change can reach since each case's last recorded pass (`evals/depends.json`, `evals/passes.json`) and records new passes.
- **`tools/eval_cost.py`**: splits an eval run's recorded cost by agent from its session transcripts (`config/projects` in the run's workspace), counting each message once and sharing each model's cost by weighted tokens.
- **`tools/model_check.py`**: reads a session's transcripts (a `.jsonl`, an eval workspace or a project's newest sessions) and reports, per agent call, the role, the model each reply ran on, the effort where recorded and the expected model (the `models` board in `.claude/devflow.json`, else the pin in `agents/*.md`, with `--escalated` and `--diagnosis` picking those rows; or a `--model` line from the step's Model line, or a `--part` line per design part, in order), marking mismatches and naming what it could not read. The board comes from `--config`, else `SOURCE/.claude/devflow.json` when SOURCE is a folder that holds one, else `.claude/devflow.json` in the current folder (for a `.jsonl` or eval workspace, run it from the project or pass `--config`); check mode names the board it read before its report. With `--board` it prints each role's model, effort, source and what a skill passes on the call, floors applied and bad entries named `ignored`; `add-feature`, `fix-bug`, `release` and `manage-project` run it before their agent calls, `add-feature` and `fix-bug` run the check at the end, and the project manager's session review reads it. `hooks/session_start.py` prints a one-line summary of the board, warning when the session's model (from the hook's input) is not the board's `orchestrator`.
- **`templates/`**: files `/devflow:setup` copies into a consumer project (profile, config, behaviour map, status file, plan, CI workflow, `CLAUDE.md` section, settings).

## Testing notes

`tests/test_guard.py` loads `hooks/guard.py` by file path and runs it against an RYOS-shaped config, a Linux-style project and a minimal config. `tests/test_session_start.py`'s `TestNextStep` covers `choose_step` and its parts (Gate, Needs, Files overlap, Who does what), and `TestMain` the `--next-step` flag. `tests/test_checks.py` builds real throwaway git repositories. `tests/test_evals.py` compiles every grader pattern in `evals/cases/` and tests the selection and record on throwaway repositories. `tests/test_skill_references.py` checks that the UI briefs in `add-feature` and `fix-bug` name the `review-ui` reference files and that they exist. `tests/test_skills.py` fails when a skill's text after its front matter reaches 19,000 characters, and checks that the stop rules open `add-feature` and `fix-bug` as their first section, in the same words. It also lints every skill: front matter with `name` equal to the folder and a 200 to 1,536-character description; every profile heading a skill cites present in `templates/devflow.md` (so renaming a heading fails CI) and setup's fixed list equal to the template's headings; and no `$ARGUMENTS`/`$N` token, `cd` into the plugin folder or development file outside `review-ui/vendor/`. Its `TestModelRules` checks the model rules are the same words in `add-feature` and `fix-bug`, the board rule the same words in those two, `release` and `manage-project`, the designer's medium pin and that `fix-bug`'s diagnosis call passes the `designer.diagnosis` row, not a literal, and that no line puts the designer's default effort above medium; its `test_no_line_gives_a_default_above_opus_medium` fails a line in the skills, agents, README, CLAUDE.md, the profile, the templates or the behaviour map that gives a default above Opus, medium. Its `TestAttributionRule` checks `add-feature`, `fix-bug`, `release` and `setup` state the attribution rule once each in the same words. `tests/test_checks.py`'s `TestAttributionCheck` runs the `attribution` check on throwaway repositories, and `TestAttributionWiring` checks the CI files, settings and configs carry it. `tests/test_model_check.py` runs `tools/model_check.py` on a fixture session with its own agent pins; its `TestRealPins.test_no_default_is_above_opus_medium` checks every real pin, phase default, general default and the diagnosis floor stay at or below Opus, medium. Behaviour changes in the guard or checks need a matching test.

## Conventions

- Hook and tool Python files carry no comments; keep it that way (the CI comment check enforces this in consumer projects, and RYOS-derived code follows the same rule).
- The plugin version lives in `.claude-plugin/plugin.json` and is bumped only in a release commit.
- RYOS keeps its own copies of these skills, agents and hooks (`add-ryos-feature`, `ryos-*`); devflow is the generalized version with project specifics moved into the profile.

## How work is done here (devflow)

This project uses the devflow plugin. Its profile is `.claude/devflow.md` (architecture rules, verify commands, edit bounds, release); its guard config is `.claude/devflow.json`.

- New capability or improvement: `/devflow:add-feature`. Bug or red CI: `/devflow:fix-bug`. Shipping: by hand, as the plan's release step, with no candidate (Standing rules in the profile); not `/devflow:release`. Status, issues, plans and decisions: `/devflow:manage-project`. Continue the plan: `/devflow:next-step`.
- What must keep working, on every surface, with the test guarding each: `docs/BEHAVIOUR.md`. Read an area's rows before changing it; a fix updates its entry and test, a new behaviour adds one.
- Project status: `docs/STATUS.md`, kept by the project manager. Plans: `docs/plans/`, one fresh coding session per step; claim the step first. Both are local and gitignored, as are `docs/archive/` and `docs/PROMPTS.md`.
- The version changes only in a `Release X.Y.Z` commit.
- **The escape rule.** Every bug found after a release gets one line in `docs/BEHAVIOUR.md` § Escapes, and its fix adds the check that would have caught it.
